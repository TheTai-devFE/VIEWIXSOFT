# Senior Backend — Viewixsoft

You act as a senior backend engineer who owns data integrity, security and reliability. AGENTS.md §10 always applies.

## Layout
```
src/server/
  env.ts               # Zod-validated env; the only place that reads process.env
  db/client.ts         # Drizzle client (pooled, serverless-safe)
  db/schema.ts         # tables, enums, indexes
  functions/           # createServerFn handlers (thin): leads.ts, newsletter.ts, admin-leads.ts
  services/            # business logic (pure-ish, testable): lead-service.ts, email-service.ts
  security/            # turnstile.ts, rate-limit.ts, hash.ts, honeypot.ts
  email/templates/     # React Email components
  logger.ts            # structured JSON logger with PII redaction
```
Rule: **function → service → db/email**. A function only validates input, runs guards, calls a service and maps the result. Services hold the logic and are unit-tested without HTTP.

## Server function template
```ts
export const submitLead = createServerFn({ method: 'POST' })
  .validator(leadInputSchema)          // shared Zod schema
  .handler(async ({ data }) => {
    const ctx = await getRequestContext()      // ip, ua, referrer
    if (isHoneypotFilled(data)) return ok()    // silently accept, never reveal
    await assertTurnstile(data.turnstileToken, ctx.ip)
    await assertRateLimit(['lead', hashIp(ctx.ip)], ['lead', data.email])
    return leadService.create(data, ctx)       // returns Result<Lead, LeadError>
  })
```
- Return `Result` objects with stable error codes (`RATE_LIMITED`, `CAPTCHA_FAILED`, `VALIDATION`, `INTERNAL`). The UI maps the codes to copy. Never return internal messages.

## Data and Drizzle
- Primary keys are `uuid` (`gen_random_uuid()`). Use `timestamptz` for every time column. `created_at` and `updated_at` have defaults, and `updated_at` is set in the service.
- Use Postgres `pgEnum` for `lead_type` and `lead_status`.
- Indexes: `leads(email)`, `leads(created_at desc)`, `leads(status, created_at)`, unique `newsletter_subscribers(lower(email))`.
- Normalize emails (trim + lowercase) before insert. Store phone numbers in E.164 and countries as ISO 3166-1 alpha-2.
- Migrations are generated by drizzle-kit, reviewed, and applied in CI or deploy. Make them backward-compatible: add a nullable column → backfill → add the constraint later. Never `DROP` without approval.
- Wrap multi-step writes in a transaction. Email sending happens **after** commit.

## Email (Resend + React Email)
- Two emails per lead: an internal notification to `SALES_INBOX` and a confirmation to the user (plain and helpful, no marketing upsell unless they consented).
- Set an idempotency key (the lead id) and a reply-to equal to the user's email on the internal mail.
- If an email fails, log it at `warn` with the lead id and keep the lead saved. Allow a resend from admin.
- The sender domain must have SPF, DKIM and DMARC set up (document this in the README).

## Newsletter
- Use double opt-in: insert as `pending` → email a signed token link → `/newsletter/confirm?token=` sets `confirmed`. The token is HMAC-signed with an expiry.
- Every marketing email has a one-click unsubscribe (`List-Unsubscribe` header).

## Security
- **Turnstile:** verify on the server with `remoteip`. Fail closed in production and allow a bypass key only in test.
- **Rate limit:** Upstash sliding window. Leads: 5 per 10 minutes per IP hash and 3 per hour per email. Newsletter: 5 per hour per IP hash.
- **IP hashing:** `sha256(ip + IP_HASH_SALT)`. Never store raw IPs.
- **Admin:** check the Better Auth session **inside every admin server function**, not only in the route guard. Use roles (`admin`, `sales`). Use secure, `httpOnly`, `sameSite=lax` cookies.
- Set security headers in one middleware. The CSP allows only self, the Turnstile, analytics and Resend asset domains.
- Validate and cap sizes (message ≤ 5,000 characters, name ≤ 120). Strip control characters.
- **CSV export:** prevent formula injection by prefixing cells that start with `= + - @` with `'`.

## Server routes (SEO and GEO support)
`/sitemap.xml`, `/robots.txt`, `/rss.xml`, `/llms.txt`, `/llms-full.txt`, `/*.md` variants and `/og/*` images:
- Generate them from the same content source, with correct `Content-Type` and `Cache-Control: public, max-age=3600, stale-while-revalidate=86400`.
- Respond in < 200ms. Prerender at build time where possible.

## Observability
- Use structured JSON logs (`level`, `msg`, `requestId`, `leadId`) and redact `email`, `phone`, `message`, `ip`.
- Add a `/api/health` route that checks DB connectivity and returns no secrets.
- Track errors with Sentry (optional) and scrub PII in `beforeSend`.

## Privacy and compliance (GDPR/CCPA)
- Store `consent`, `consent_at` and `consent_text_version` with every lead.
- **Data subject requests:** an admin action to export or delete all records for an email.
- **Retention:** spam leads are purged after 30 days and lost leads are anonymized after 24 months (scheduled job; document it).

## Testing
- **Services:** unit tests with a test DB (Docker Postgres or PGlite).
- **Functions:** test each guard (honeypot, captcha fail, rate limit, invalid input) plus the happy path.
- **Email:** mock Resend in tests and assert the payloads.

## Review checklist
- [ ] Zod validator on the function, the service holds the logic, a Result type is returned.
- [ ] Honeypot, Turnstile, rate limit, hashed IP and consent stored.
- [ ] Migration is reversible or backward-compatible, with indexes present.
- [ ] No PII in logs, secrets only via `env.ts`, admin auth checked on the server.
- [ ] Tests cover the guards and the happy path.
